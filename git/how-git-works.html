Frame 1 · a9f3d21 — the first commit. Three files, three new objects written to .git/objects.

$git hash-object -w app.js

The name of a thing is the hash of a thing

Git's storage is one flat key–value store. The key is always a SHA of the value, so nothing is ever stored under a name you chose.

To store a file, Git takes its raw bytes, prepends a tiny header (blob 128\0 — the type and the byte count), and hashes the whole thing. That produces 40 hex characters. It compresses the bytes and writes them to a path built from the hash itself: the first two characters become a directory, the rest become the filename.

Two consequences fall straight out of this, and almost everything else in Git is downstream of them. Identical content is always stored once, no matter how many files, folders or commits contain it. And changing one byte produces a completely unrelated hash — so Git can decide whether two things are the same by comparing 40 characters, without ever opening them.

Worth knowing

A blob holds contents and nothing else: no filename, no path, no timestamp, no permissions. That information lives one level up, in trees.

$git cat-file -p HEAD^{tree}

Three kinds of object, and that is the whole database

Everything Git stores is a blob, a tree, or a commit. They are all addressed by hash, and they only ever point downwards.

A blob is the contents of one file. A tree is a directory listing: a list of rows, each holding a mode, a type, a hash and a name. A tree can name blobs (files) and other trees (subdirectories). A commit names exactly one tree — the root of your project at that instant — plus its parent commit(s), the author, the date and your message.

So a commit does not contain a change. It contains a complete, addressable picture of every file you were tracking, reachable by following hashes down from the root tree.

$git cat-file -p 4c1b7ec^{tree}

A full snapshot that costs one file

This is the part that sounds wasteful and isn't. Each commit records everything, yet only genuinely new content is ever written.

When you edit one file and commit, Git writes a new blob for that file, a new tree for each directory on the path up to the root, and one new commit. Every other entry in those trees still holds the old hash — the same object, shared between both snapshots.

$git status

Your file exists in three places at once

Most confusing Git messages are just Git reporting a mismatch between two of these three.

The working tree is the ordinary files on your disk — Git is not watching them. The index (also called the staging area) is a single binary file, .git/index, holding a flat list of every tracked path with the blob hash it should have and some stat data for speed. The object database is .git/objects, the permanent store from the sections above.

git add hashes the file on disk, writes the blob, and updates that path's row in the index. git commit turns the index into trees, writes a commit pointing at the root tree, and moves your branch. Nothing is scanned for changes at commit time — the index already knows.

$git cat-file -p HEAD:notes.txt

Two walkthroughs: one line added, one line removed

Both look like one-line events in a diff. Neither is stored as a line operation anywhere — and the hashes below are the real ones, reproducible in any repository.

Start from one committed file, notes.txt: three lines, 17 bytes.

alpha ¶ beta ¶ gamma ¶  →  blob 85c3040  ·  root tree e60c60d  ·  commit 1

Case 1 — a line is added

You append delta and commit. git add hashes the file as it now stands — all four lines, 23 bytes, plus the blob 23\0 header — and gets 7a28df3…, an address the store has never seen. So Git writes a new object holding the complete new contents of the file, compressed whole. The old blob 85c3040… is not consulted, not modified and not deleted; it still holds the three-line version, and commit 1 still reaches it.

Then the tree. A tree row is (mode, type, hash, name), and here only the hash changed — so Git writes a new root tree, 2bec8c1…, identical to the old one except that the notes.txt row points somewhere else. Had notes.txt lived in docs/, every tree from docs/ up to the root would be rewritten too, each one purely because a hash inside it moved.

Then one commit object naming tree 2bec8c1… and parent commit 1. Three objects for one added line — and not one of them contains the idea of an addition.

Case 2 — a line is removed

Same starting file. You delete beta and commit. The mechanics do not change at all: Git hashes the two remaining lines — 12 bytes — and gets 7819bf7…, again unseen, again written as a complete object holding the file's full new contents. A smaller file, but still a whole new object, not a shortened one.

There is no tombstone. No object anywhere says a line went away. The root tree becomes cb2188c…, its notes.txt row now naming 7819bf7…, and a new commit names that tree. Deleting the file instead would differ by exactly one step: the new tree would be written with that row missing and no blob would be written at all — but 85c3040… would still sit in the store, reachable from every commit that named it.

Which is why removing a line, or a file, never frees space in history. The bytes are still addressed by a commit you can still check out.

The symmetry that gives it away

Put beta back, exactly as it was, and commit again. Git hashes the file, gets 85c3040… — already in the store — and writes no blob at all. The new tree simply names the original object again. An undo costs less than the change did, because content that has ever existed never needs storing twice.

And the obvious objection

Yes: one changed line in a 10 MB file writes a fresh 10 MB blob. That is true while the object is loose, and it is what the model costs to stay this simple. Packing — further down — is where the near-duplicate finally gets stored as a delta, as compression underneath, without anything above it changing.

$git diff 4c1b7ec e07a559

The diff is a calculation, not a record

Nowhere in .git is there a file containing @@ -14,7 +14,9 @@. That text is produced on demand, from two snapshots, and thrown away.

When you ask for a diff, Git picks two sides — two commits, or the index and the working tree, or HEAD and the index — and walks their trees in parallel, name by name:

Same hash on both sides? Skip. And if the matching entry is a directory, skip the whole subtree at once, without reading a single byte of it. This is why git diff stays instant in a repository with a hundred thousand files: almost every comparison is 40 characters against 40 characters.

Different hash? Then, and only then, Git loads both blobs, splits them into lines, and runs a diff algorithm (Myers by default; --histogram and --patience are alternatives that pick different, sometimes tidier, ways to line the two files up). The hunks, the + and - prefixes and the three lines of context around each change are formatting applied to that result.

The tell-tale case

Git never records that you renamed a file. When git diff shows renamed: old.js → new.js, it noticed a blob that vanished from one tree and an identical or very similar blob appearing elsewhere, and guessed — at display time, with a similarity threshold you can tune via -M. Change the threshold and the same two commits produce a different-looking history.

$cat .git/refs/heads/main

A branch is a file with a hash in it

41 bytes: forty hex characters and a newline. That is the entire implementation of a branch.

Commits point backwards to their parents, and nothing points forwards. So to know where "the end" of a line of work is, Git keeps refs: small files under .git/refs/ naming one commit each. HEAD is a file too, usually containing ref: refs/heads/main — a pointer to a pointer.

Committing means: write the objects, then overwrite that 41-byte file with the new commit's hash. Branching means writing a new 41-byte file. Nothing is copied, and no history is duplicated — which is why creating a branch in a huge repository is instant.

$git merge-base main feature

Merging compares three snapshots, not two

Because parents are recorded, Git can find where two branches last agreed — and that third point is what makes automatic merging possible.

Git walks backwards from both tips until it finds their best common ancestor, the merge base. Then, for each file, it looks at three versions: base, yours, theirs. If only one side's hash moved away from the base, that side wins, silently. If both moved, Git tries to combine them line-region by line-region — and if the two sides changed overlapping regions, it stops and writes the conflict markers into your working tree for you to resolve.

A conflict is therefore not "Git got confused". It is a precise statement: both sides edited the same region relative to their last agreement, and choosing between them is a judgement call.

$git gc

The one place deltas are real

Deltas do exist in Git — just not where people assume, and not as part of the model.

Objects are written individually at first ("loose"). Periodically, Git packs thousands of them into a single .pack file, and in there it does store some objects as deltas against a similar object, on top of zlib compression. But those deltas are chosen by heuristics — similar size, type and path name — not by your history. A blob may be stored as a delta against a version from a different branch entirely, or against a newer one rather than an older one.

It is a compression detail underneath a stable interface. Ask for any object by hash and you get back the complete content, reassembled if needed. Nothing above that layer knows or cares.

What your everyday commands actually do

git add fileHash the file, write a blob if that content is new, update one row of the index.
git commitTurn the index into trees, write a commit pointing at the root tree and the current HEAD, move the branch ref.
git statusCompare working tree ↔ index ↔ HEAD's tree, using stat data and hashes.
git diffWalk two trees, skip matching hashes, run a line diff on the blobs that differ.
git log -pWalk the parent chain and recompute a diff for each step, on the fly.
git checkout branchRead that branch's tree into the index and the working tree, point HEAD at it.
git reset --hardMove the ref, then overwrite index and working tree from the target commit's tree.
git cherry-pickCompute a patch from a commit, apply it here, write a brand-new commit — new content, new hash.
The model in one sentence

Git stores immutable snapshots addressed by the hash of their contents, shares every unchanged object between them, and computes differences between snapshots whenever you ask.

Try it on a real repository: git cat-file -p HEAD prints a commit, git cat-file -p HEAD^{tree} prints its root tree, and git cat-file -p <hash> prints any object you find inside. Two or three of those and the model stops being abstract.
