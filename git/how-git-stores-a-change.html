The confusion worth clearing up first

"Git stores complete files" and "Git only pays for the change" are both true. They are answers to different questions, and the whole knot comes undone once you stop asking them at the same time.

What just happened, in totals

Three commits. Two versions of the file. And the store holds seven objects: 2 blobs, 2 trees, 3 commits — not nine, because the third commit found both its blob and its tree already sitting there.

That is the deduplication, and notice where it came from. Nobody compared anything. Removing the two lines produced a file whose bytes hash to ae121a6…, and that address was already occupied. Git wrote nothing because there was nothing new to write. The same mechanism that makes an unchanged file free makes an undone change free.

The thing to notice

There is no state anywhere in that lab. No history, no previous value, no diff. The address is a pure function of the bytes — which is the only reason "I have seen this content before" can be a lookup instead of a search.

Now the other layer: where the delta lives

Two complete blobs exist. Below them, in the packfile, one of the two is stored as instructions for rebuilding it out of the other.

A Git delta is not a diff. It has no notion of a line, and it never says "added" or "removed". It is a tiny program in two instructions — COPY offset, length (take a run of bytes from the base) and INSERT bytes (here are some literal bytes that aren't in the base) — run against a base object to reproduce a target object byte for byte.

Lab 3 · the delta, disassembled

Instruction sizes follow Git's real encoding: a copy is one opcode byte plus only the non-zero bytes of its offset and length; an insert is one opcode byte per run of up to 127 literal bytes; the header carries both object sizes as varints. The result is then zlib-compressed, which is why the measured on-disk numbers further down are in the same ballpark rather than exactly equal.

Read the reverse direction again

Rebuilding the ten-line file from the twelve-line one takes two copy instructions and no literal bytes at all. The delta does not contain a single character of your file. It says: take the first 49 bytes of that other object, then take 50 bytes starting at offset 78, stop.

That is what "removing two lines" looks like down here. Not a subtraction, not a tombstone — a shorter set of copy instructions. And it is why the direction Git happens to pick barely matters for cost: an insertion costs the inserted bytes, a removal costs nothing but a second copy instruction.

When the delta appears: the encoding phase

Nothing above has said when. That turns out to be the whole misunderstanding: the delta does not exist at commit time. It is created later, by a separate process, and thrown away and recreated every time that process runs.

git add and git commit never write a delta. They write complete, standalone, literal objects — always. The delta is produced by git gc / git repack, which rewrites the loose objects into a packfile and deletes the originals. Two separate events, often thousands of commits apart.

The same repository at three moments

Real measurements, one 489 KB file, two lines inserted in the middle:

momentwhat is in .git/objectsbytes on disk
after commit 1one complete blob, zlib'd, loose26,667
after commit 2two complete blobs — no delta anywhere53,423
after git gcone literal base + one 53-byte delta, packed28,713

The middle row is the one that resolves the argument. Between the second commit and the next gc, your repository genuinely does hold two complete copies, and the disk usage genuinely does double. The intuition that "two complete files must cost two complete files" is not wrong — it is right, for that window of time. What it misses is that a later, entirely separate step comes along and re-encodes them.

And it only happens when it pays

"Base + delta" is not how Git stores things. It is an optimisation Git sometimes applies, and it needs all five of the conditions in that dark box to line up. Miss any one and the object is stored literally — which is the common case, not the exception. In a pack I built from 60 commits, 35 of the 60 blobs were literal and only 25 were deltas, and every commit object was literal.

The clearest way to see this is a repository too small to bother with. Ten lines, two commits, six loose objects totalling 491 bytes:

a 71-byte file, two commitsbytes on disk
six loose objects491
after git gc — every object still literal, zero deltas3,089

Packing made it six times bigger. The pack index and its fixed overhead dwarf any saving available on 491 bytes of content, and Git correctly declined to delta anything. A small repository with two versions of a small file simply holds two complete objects, forever, and that is the right answer.

And measured, for real

I ran exactly the scenario above — 10,000 lines, insert two in the middle, commit, remove them, commit — in a throwaway repository, then asked Git what it actually stored:

The second complete 488,894-byte file costs 53 bytes. Not 53 kilobytes. Fifty-three bytes, because it is a handful of copy instructions and a header, and the literal content it needs is already sitting in the object next to it.

Note which one Git chose as the base: the newer, larger blob is the full copy, and the older one is the delta. Nothing about your history decided that. The packer sorts objects by type, path and size, slides a window over them, and picks whatever compresses best — it generally prefers newer objects as bases, on the theory that recent versions get read more often. Repack tomorrow and it may choose differently. Both hashes stay exactly the same.

Where it stops working

All of this rests on consecutive versions being byte-similar. Text, source code, CSV, SVG: excellent. Anything already compressed or encrypted — .zip, .png, .mp4, .psd, encrypted archives — changes everywhere when it changes anywhere, so COPY instructions find nothing to copy and the delta degenerates into the whole file. A thousand revisions of a 50 MB binary really does cost 50 GB. That is not a bug in the model, it is the model working exactly as described with content that defeats the optimisation, and it is why git-lfs exists.

The statements worth having

Every one of these is a place the intuition goes wrong for a good reason — each is either true of some other system, or true of Git at a different moment. They are listed in the order they tend to bite.

  1. Git records the line I added, and points at the part of the file that stayed the same.

    Git records a complete snapshot. The added line exists only as the difference between two whole files, and only when something computes it.

    This is how CVS and SVN genuinely worked, which is why the intuition is so durable. Git inverted it: snapshots are the model, and differences are calculated on demand.

  2. The delta is built when the new blob is created, during add or commit.

    add and commit always write complete, standalone, literal objects. Deltas are created later, by gc / repack, which then deletes the loose originals.

    Two separate events. Between them, the repository really does hold both complete files — 53,423 bytes in the measurement above.

  3. Storage is always base + delta.

    Deltas are conditional. The objects must be packed, large enough, similar enough, near each other in the packer's window, and the delta must come out smaller than storing it literally.

    In a 60-commit pack, 35 of 60 blobs were literal. In a repository with a 71-byte file, nothing is delta'd at all and gc makes it six times bigger.

  4. COPY 0,49 copies those 49 bytes into the delta, so the delta must be as big as the file.

    COPY is an instruction of about four bytes naming a byte range. It carries no content. 53 bytes of instructions describe 488,894 bytes of output.

    A recipe that says "same as page 12, plus two spoons of sugar" fits on a card without containing a cake.

  5. The copied parts are shared objects — the target holds references to pieces of the base.

    No sub-objects exist. A delta names one other object, which is itself a complete file, and then indexes byte ranges inside it by integer offset.

    There are two unrelated kinds of sharing in Git: permanent, hash-addressed sharing between trees and blobs, and temporary, offset-addressed byte reuse inside one packfile. Only the first is visible in the model.

  6. A blob is a map of the pieces its file is made of.

    A blob is a complete file. Sometimes its current encoding is a short recipe referring to a neighbour — but the encoding is not the blob, and most blobs have no such recipe.

    The design being described is real: restic, borg, IPFS and block-level dedup do store files as manifests of chunk hashes. Git refuses to, because it wants the address of a file to be the hash of that file's bytes and nothing else.

  7. Two complete blobs must occupy two complete files' worth of disk.

    "Complete" describes what you get back, not the room it takes. A single ordinary blob, with no delta anywhere, already occupies about 5% of its content size.

    zlib finds repetition inside one object; a delta finds it between two. Same trick, wider scope. The premise breaks before deltas are even involved.

  8. The objects in .git/objects are the current snapshot.

    The object store holds every version from all of history, plus objects nothing points at any more. The current snapshot is a path through it: HEAD → commit → tree → blobs.

    Checking out an old commit does not change the store at all — it rewrites the working tree and the index. Orphaned objects surviving there is exactly what makes git reflog able to rescue work.

  9. Resolving a delta writes the reconstructed file to disk.

    It builds the file in memory and frees it. .git/objects is byte-for-byte identical before and after a read.

    Only checkout / restore / switch writes a file, and that is a separate act with a different purpose: populating your working tree.

The shape of every one of these

Each mistake collapses two layers into one — either the model into the storage, or one moment in time into another. Keeping blob separate from encoding, and commit time separate from pack time, resolves all nine.

Interrogate your own repository

Nothing above needs to be taken on trust. These four print the real state of any repository you have:

commandwhat it tells you
git count-objects -v -Hhow much is loose versus packed, right now
git cat-file --batch-all-objects --batch-check='%(objecttype) %(objectname) %(objectsize) %(objectsize:disk) %(deltabase)'every object, its logical size, its real size on disk, and whether it is a delta and against what
git verify-pack -v .git/objects/pack/*.idxhow each object in a pack is encoded, with chain depths and base offsets
git hash-object <file>the address any content would take, without writing anything

The second one is the interesting one. Run it on a repository you have worked in for a year and sort by the disk column — you will find objects whose logical size is megabytes and whose real cost is a few dozen bytes, sitting beside others that were never worth deltaing at all.

So: does Git save both complete files?

Yes — and it pays for one and a half of them.

Both blobs are complete, both are addressable, both can be read on their own in one step. Ask for either hash and Git hands you 489 KB, without walking your history, without replaying anything, and just as fast for a commit from five years ago as for the one you made this morning. That is the guarantee, and it never bends.

Underneath — and only after gc has run, and only because these two happened to be worth it — one of them is 53 bytes of copy instructions. That is not the model relaxing. It is zlib and a delta encoder doing their job under a floor the model never lets you see through, on a schedule that has nothing to do with when you committed.

The version-control systems Git replaced made the opposite trade: the storage layer was the model, a file was genuinely a base plus a chain of accumulated edits, and reading an old revision meant replaying that chain. Cheap to store, and slower the further back you looked. Git decided that snapshots are what you reason about, and that saving space is a compression problem to be solved separately, invisibly, and rearranged whenever convenient.

Which is the sentence that dissolves the confusion, if you want to carry one away:

Carry this one

Git stores snapshots and compresses them well. It does not store changes and reconstruct snapshots. Every "but surely it just saves the diff" question is really a question about the second layer — and the answer is always: sometimes, later, by a process that reads no history, and it makes no difference to what anything means.
