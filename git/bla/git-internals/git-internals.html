1. The big idea: a content-addressed filesystem

Most people think of Git as "a tool that tracks changes to files". Under the hood it is something simpler and stranger: a key-value store. You hand Git some content, it hands you back a 40-character SHA-1 hash — the key. The content is stored in a file named by that hash inside .git/objects/.

Everything in Git — file contents, directories, commits, tags — is an object in this store, addressed by the hash of its own content. This is called content-addressable storage.

Two immediate consequences fall out of this design:

  • Identical content is stored only once. If two files have the same bytes, they are the same blob. If a file doesn't change between commits, the new commit simply points at the existing blob.
  • Nothing can change silently. Change one byte of an object and its hash changes. The hash is a checksum of the content, so corruption and tampering are detectable by construction.

The hash of the content is the key; the content is the value. The hash is derived from the content, never assigned.

On disk, objects live at .git/objects/<first 2 chars of hash>/<remaining 38 chars>, zlib-compressed. Try it yourself:

# store content without creating a file at all
$ echo "hello world" | git hash-object --stdin
3b18e512dba79e4c8300dd08aeb37f8ebc8f4bc

# -w actually writes the object into .git/objects
$ echo "hello world" | git hash-object -w --stdin
$ find .git/objects -type f
.git/objects/3b/18e512dba79e4c8300dd08aeb37f8ebc8f4bc

2. The four object types

Every object in the store is one of exactly four types. Everything else in Git (branches, the index, remotes) is built on top of these.

blob — file content tree — directory commit — snapshot + history tag — annotated pointer
TypeStoresPoints to
blobRaw bytes of one file (no name, no metadata)nothing

commitSnapshot metadata: author, message, parentsone tree + parent commits
tagAnnotated tag: tagger, messageusually a commit

A commit points to a tree; trees point to blobs and subtrees. Blobs point at nothing — they are the leaves.

3. The blob: your file's content, and nothing else

A blob (binary large object) is the raw content of one file. Crucially, a blob does not know its own filename, permissions, or which directory it lives in. It is just bytes.

This is why Git can deduplicate: rename a file, and no new blob is created — the same blob is simply referenced from a different place. Change one line of a 100 MB file, and Git stores a new blob with the full new content (later, during packing, it computes deltas to save space — but conceptually each version is a full snapshot).

Two files named readme.md with identical content map to one blob. The name lives in the tree, not the blob.

4. The tree: a directory snapshot

A tree represents one directory. It is a flat list of entries, each with a mode, a name, and the hash of a blob or another tree:

Trees nest: a tree entry can point at another tree, which is how subdirectories work. A commit's tree is the root, and following it recursively gives you the complete state of every file in the project at that moment.

Directories become trees; files become blobs. The filename exists only as an entry inside a tree.

5. The commit: a pointer to a tree (plus history)

Here is the key mental shift: a commit is not a diff. A commit is a snapshot of the entire project, encoded as a pointer to a root tree. It also records metadata and the hash(es) of its parent commit(s), which is where "history" comes from.

$ git cat-file -p HEAD
tree 8f3c2a1b4d5e6f708192a3b4c5d6e7f8091a2b3c
parent 91c4d2e5f6a708192a3b4c5d6e7f8091a2b3c4d
parent 2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e   ← second parent = merge commit
author Jane Doe <jane@example.com> 1724700000 +0200
committer Jane Doe <jane@example.com> 1724700000 +0200

A commit's hash covers its content and its parents. Because each commit's hash includes its parent's hash, the chain is tamper-evident all the way back: rewrite any old commit and every descendant hash changes. This is why "rewriting history" means creating entirely new commits.

A commit = one snapshot (tree) + links to the past (parents) + metadata.

6. How commits form history

Each commit points to its parent(s), so history is a directed graph that grows forward in time and is read backward. A normal commit has one parent; a merge commit has two or more; the initial commit has none.

Arrows point from child to parent: each commit knows where it came from, not what came after.

7. Refs and HEAD: naming the tips

Hashes are unwieldy, so Git gives them names. A ref is a tiny text file containing one hash:

.git/HEAD                → "ref: refs/heads/main" (symbolic)
.git/refs/heads/main     → 4a5b6c7d8e...   (the commit main points to)
.git/refs/heads/feature  → 91c4d2e5f6...
  • A branch is nothing but a ref that moves forward when you commit. There is no branch object, no branch history — just a 41-byte file.
  • HEAD is a symbolic ref: it names the branch you have checked out (or, in "detached HEAD" state, a raw commit hash).
  • Tags are refs too — lightweight tags point straight at a commit; annotated tags point at a tag object, which points at the commit.

The full pointer chain from a human-friendly name down to raw file content.

8. How the SHA-1 is computed

An object's key is the SHA-1 of a small header followed by the content. The header is the object type, a space, the byte length, a NUL byte — then the payload:

hash = SHA1( "<type> <size>\0" + content )

# e.g. for a blob containing "hello world\n":
$ printf "blob 12\0hello world\n" | sha1sum
3b18e512dba79e4c8300dd08aeb37f8ebc8f4bc

Because the type and size are part of the hash, a blob and a tree can never collide by accident, and the hash pins the object's entire identity.

9. Putting it together: add and commit

Now the everyday commands make sense in object terms:

git add writes blobs and records them in the index; git commit turns the index into a tree, wraps it in a commit, and moves the branch ref.

Step by step, what git add app.py + git commit -m "fix" actually do:

  1. add: compress app.py's content, write a blob object (if that content doesn't already exist), record app.py → <blob hash> in the index.
  2. commit: write tree objects from the index (nested directories become nested trees).
  3. commit: write the commit object: root tree hash, parent = current HEAD commit, author, message.
  4. commit: update refs/heads/main to the new commit's hash. Done — the "branch" has moved.

10. Plumbing commands cheat sheet

Git's low-level ("plumbing") commands let you inspect the object database directly:

# what type is this object? (-t) / print its content (-p)
$ git cat-file -t  3b18e51          → blob
$ git cat-file -p  3b18e51          → hello world

# list a tree without switching to it
$ git ls-tree HEAD src

# every object in the store, with type and size
$ git cat-file --batch-all-objects --batch-check

# everything reachable from all refs (garbage-collection view)
$ git rev-list --all --objects

# where a blob's content lives across history
$ git log --all --oneline -- path/to/file
The one-sentence summary: a commit is a named snapshot whose hash chains it to its parents; a tree is a directory listing mapping names to blobs and subtrees; a blob is file content with no name and no history. Branches, HEAD, tags, the index — all of it is bookkeeping on top of this object graph.
